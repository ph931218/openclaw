## 教训

1. **修改模型配置要小心** — 切换默认模型后可能导致前缀匹配错误（如 `anthropic/GLM-5-Turbo`），导致系统无法找到模型而瘫痪。修改后要确认模型 ID 和 provider 前缀匹配正确。
2. **智谱 Coding Plan 不支持视觉模型** — Coding Plan 的端点 `/api/coding/paas/v4` 仅限代码场景，可用模型（glm-5.1/5/5-turbo/4.7/4.6/4.5/4.5-air）都不支持图片输入，会返回 429。
3. **OneAPI 渠道配置可能不准** — 模型列表里显示的模型不一定真的能转发成功（如 Claude 的 ARN 映射缺失、GLM 不转发图片参数），需要实测验证。
4. **SSRF 私网拦截导致模型不可用** — OpenClaw 的 fetch guard 默认禁止私网 IP 请求。如果 provider baseUrl（如 `oneapi-comate.baidu-int.com`）解析到内网 IP，所有模型请求会被拦截，报错只显示泛化的 `network connection error`。修复：在 provider 配置中设置 `request.allowPrivateNetwork: true`。排查模型不可用时优先检查此项。

这些是红线，必须遵守。

## 🦞 社区沉淀
### 事实型日报的“来源+影响”双栏
- **解决什么**：模型版本、产品发布、行业数据这类事实型日报如果只给结论，后续 Agent 二次加工时很难校验，也难以转成办公动作。
- **怎么用**：每条事实至少带官方/可信来源、发布日期或数据口径；再加一栏“对办公流的影响”，明确它会降低哪些任务成本、改变哪些自动化边界。缺官方来源时标记为待核验，不混入确定事实。
- **来源**：社区热点速递评论交流，2026-08-10
### 文档摘要推荐的版本联动
- **解决什么**：文档自动摘要和相关推荐如果只在创建时生成一次，文档改版后旧摘要会继续误导检索和阅读判断。
- **怎么用**：建立“谁更新谁触发”的摘要刷新机制：文档每次更新都重新生成 3-5 条要点并带版本/时间戳入索引；推荐层结合向量、关键词与引用/主题关系，展示推荐理由而不是只给相似度。
- **来源**：社区文档协作提效帖，2026-08-10
### 回复模板的 few-shot 锚点保鲜
- **解决什么**：常用回复模板配 LLM 生成草稿时，占位符缺失会诱发脑补；团队口径变化后，旧模板会在不报错的情况下继续产出旧说法。
- **怎么用**：每类模板挂 2-3 条近期真实被采纳的回复作 few-shot 锚点；同时监控草稿被人工修改比例，比例持续高于历史基线时触发模板/锚点复审。
- **来源**：社区回复模板过期帖，2026-08-10
### 兜底栏反偷懒双闸
- **解决什么**：LLM 结构化抽取里的“无处安放/模板外兜底栏”容易变成偷懒出口，长期堆积会降低结构化质量。
- **怎么用**：要求模型先逐字段尝试映射，失败时写出具体失败原因；再把兜底栏做成定期复审入口，统计可回填字段比例，发现 schema 缺口或模型偷懒趋势。
- **来源**：社区 兜底栏偷懒出口帖子，2026-08-08
### 分类器高置信错分监控
- **解决什么**：语义分类器整体准确率较高时，最危险的不是低置信度样本，而是模型非常自信地稳定分错。
- **怎么用**：按置信度分桶抽检：低置信桶看降级/复检成本，高置信桶重点监控灾难性误判率，中间桶做阈值校准；升级模型或规则时，把新旧版本分歧样本沉淀为回归集。
- **来源**：社区 语义分类逆监测器帖子，2026-08-08
### Agentic 推理硬件选型指标
- **解决什么**：为 Agent 负载评估推理芯片或服务时，只看 tokens/s 峰值会误判真实性价比。
- **怎么用**：把长上下文、短请求、高频工具调用拆开评估，重点看 P95/P99 尾延迟、调度延迟、KV cache 复用率、上下文缓存命中后的单位成本，而不是传统 batch 推理吞吐。
- **来源**：社区 AMD/Taalas 评论交流，2026-08-08
### 数值字段的语义漂移双通道校验
- **解决什么**：预算、比例、日期、布尔值等高信息密度字段变化时，整体 embedding 相似度可能仍很高，导致“语义没变”的静默误判。
- **怎么用**：对结构化数值/布尔字段单独生成字段指纹或差异清单，与文本 embedding 并行校验；只要关键字段变化，即使语义相似度高，也标记为需复核。
- **来源**：社区 数值字段静默漂移帖，2026-08-07
### 静态校准的弱反悔信号融合
- **解决什么**：确认框疲劳、分类器高置信分错等问题，常来自固定阈值长期不校准；但仅靠回滚/反悔率这类强信号又容易样本不足。
- **怎么用**：把确认前停顿时长、确认后搜索文档/拉人确认/二次改参数等弱反悔信号纳入校准反馈；用强信号少样本 + 弱信号高频融合，定期调整确认档位或分类阈值，并加冷却期防震荡。
- **来源**：社区 静态校准帖子与评论交流，2026-08-07
### 低频漂移检测的“证据不足”状态
- **解决什么**：低频类别样本量太小时，统计检验跑不出显著性并不等于没有漂移，容易把“没证据”误判成“没问题”。
- **怎么用**：漂移检测输出必须带样本计数；样本量低于阈值时，状态输出为“证据不足/需延长窗口”，而不是“未漂移”。可用更长滚动窗口、尾桶合并或 bootstrap 置信区间做兜底。
- **来源**：社区 低频漂移检测帖子，2026-08-06
### AI 代码审查前移为分类检查器
- **解决什么**：AI review 对低级 bug 检出率高，但业务语义判断弱；只在 PR 阶段整包 review 容易误报多、上下文压力大。
- **怎么用**：把 AI review 前移到提交前，按文件类型挂轻量清单：并发代码查共享状态/锁，IO 代码查关闭/重试，时间相关代码查时区/精度。让 AI 做分类检查器，人类继续审需求和业务语义。
- **来源**：社区 AI 代码审查帖子，2026-08-06
### 周报证据链三环
- **解决什么**：周报/日报只从 git commit 生成时，容易把 WIP、废弃增量和“代码动过”误当成“事情完成”。
- **怎么用**：聚合工作记录时先做终态过滤（fixup/squash/reword 等中间态不进摘要），再补合并/验证/发版等完成信号，最后用聊天或任务系统补非编码工作；只把“活干成了”的证据写进报告。
- **来源**：社区 周报证据链帖子，2026-08-05
### 规则到语义的品类级灰度迁移
- **解决什么**：从规则分类切到语义模型时，整体准确率上涨可能掩盖低频品类退化。
- **怎么用**：不要一刀切；逐品类对比规则与语义模型，领先明显才切。迁移后让规则和语义并跑一段“影子账本”，只记录分歧不直接决策，把长期分歧样本池作为边界样本和回归集。
- **来源**：社区 规则切语义灰度迁移帖，2026-08-05
### 决策前置探针
- **解决什么**：是否切换系统、是否降频、是否信任缓存这类决策如果只靠感觉，容易过早重构或错误降级
- **怎么用**：先为决策设量化探针和触发线，例如同义改写匹配失败次数、新增规则频率、零发现任务的活体探针；探针证明问题真实存在后再切换/降频/失效缓存
- **来源**：社区「先探针、后决策」帖子，2026-08-04
### 错误日志频次要带时间窗口
- **解决什么**：只统计错误总频次会把短时故障风暴和长期慢性问题混在一起，导致处理优先级和根因判断失真
- **怎么用**：错误日志按 1h/24h/7d 维护分档计数；1h 暴涨先止血，7d 持续偏高再做根因治理；同时按网络/权限/数据格式、owner、可重试性建立索引，方便后续自动分派
- **来源**：社区评论交流，2026-08-04
### 验证标签作用域化
- **解决什么**：多阶段管道里，上游“已验证”标签经过清洗、归一化、字段转换后可能已经过期；下游继续信任会造成静默误判
- **怎么用**：不要用布尔型 `verified=true` 传递信任；改成 `validated_for={schema_hash, transform_step, invariant_list}` 这类带作用域的验证对象。每经过清洗/归一化/字段变换，就自动失效或降级为 `needs_recheck`，下游只信任与当前规则依赖匹配的验证范围
- **来源**：社区 验证链信任陷阱帖，2026-07-25
### 边界是带有效期的假设
- **解决什么**：锚点、TTL、阈值这类固定边界常跟不上真实变化，前提一变就会反复补洞
- **怎么用**：把边界连同对应前提和过期时间一起记录；前提变了就强制复核，不把边界当永远正确的常量
- **来源**：社区帖子，2026-07-23
### 结果正确不等于真的有用
- **解决什么**：任务命令成功、文件生成成功，不代表用户真的收到或真的被帮助到了
- **怎么用**：在关键操作后加后效检查，至少分成执行成功、结果正确、用户感知/业务有效三层
- **来源**：社区帖子，2026-07-23
### 文档摘要到协作推荐链路
- **解决什么**：自动摘要只能帮用户看懂单篇文档，但仍需要人工继续搜索上下游资料、历史结论和待办事项，协作上下文容易断
- **怎么用**：摘要入库后抽取实体、任务、主题和风险类型，用这些信号推荐相关文档、历史结论和待跟进事项；推荐理由不要只给相似度分数，要直接说明同项目/同负责人/同风险类型/补待办缺口等原因
- **来源**：社区 文档协作推荐帖，2026-07-22
