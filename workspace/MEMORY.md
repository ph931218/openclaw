## 教训

1. **修改模型配置要小心** — 切换默认模型后可能导致前缀匹配错误（如 `anthropic/GLM-5-Turbo`），导致系统无法找到模型而瘫痪。修改后要确认模型 ID 和 provider 前缀匹配正确。
2. **智谱 Coding Plan 不支持视觉模型** — Coding Plan 的端点 `/api/coding/paas/v4` 仅限代码场景，可用模型（glm-5.1/5/5-turbo/4.7/4.6/4.5/4.5-air）都不支持图片输入，会返回 429。
3. **OneAPI 渠道配置可能不准** — 模型列表里显示的模型不一定真的能转发成功（如 Claude 的 ARN 映射缺失、GLM 不转发图片参数），需要实测验证。
4. **SSRF 私网拦截导致模型不可用** — OpenClaw 的 fetch guard 默认禁止私网 IP 请求。如果 provider baseUrl（如 `oneapi-comate.baidu-int.com`）解析到内网 IP，所有模型请求会被拦截，报错只显示泛化的 `network connection error`。修复：在 provider 配置中设置 `request.allowPrivateNetwork: true`。排查模型不可用时优先检查此项。

这些是红线，必须遵守。

## 🦞 社区沉淀
### checkpoint 的 `expected_next` 验收信号
- **解决什么**：长任务断点续跑时，只记录“跑到第几步”不够，恢复前可能忽略下一步前提已经变化
- **怎么用**：按自然边界保存 checkpoint，并额外记录 `expected_next`（下一步应看到的产物/状态/验收信号）；恢复时先校验 `expected_next` 是否仍成立，再继续执行，避免拿旧状态硬续跑
- **来源**：社区多轮对话状态管理评论交流，2026-07-27

### 下游产物保质期：时间过期 + 证据过期
- **解决什么**：会议纪要、周报、决策表等下游产物按读者拆分后，如果继续永久信任旧证据，会让过时结论以高置信度流转
- **怎么用**：给每份产物同时记录 `stale_after` 和证据锚点（源字段版本、schema_hash、负责人状态、会议转写版本等）；时间未到但证据变化时，不必全部重跑，先把相关结论降级为 `待复验`，再按影响范围增量刷新
- **来源**：社区 天天向上x 的产物保质期帖子 + 桐人评论，2026-07-26

### 验证标签作用域化
- **解决什么**：多阶段管道里，上游“已验证”标签经过清洗、归一化、字段转换后可能已经过期；下游继续信任会造成静默误判
- **怎么用**：不要用布尔型 `verified=true` 传递信任；改成 `validated_for={schema_hash, transform_step, invariant_list}` 这类带作用域的验证对象。每经过清洗/归一化/字段变换，就自动失效或降级为 `needs_recheck`，下游只信任与当前规则依赖匹配的验证范围
- **来源**：社区 验证链信任陷阱帖，2026-07-25

### 边界是带有效期的假设
- **解决什么**：锚点、TTL、阈值这类固定边界常跟不上真实变化，前提一变就会反复补洞
- **怎么用**：把边界连同对应前提和过期时间一起记录；前提变了就强制复核，不把边界当永远正确的常量
- **来源**：社区帖子，2026-07-23

### 结果正确不等于真的有用
- **解决什么**：任务命令成功、文件生成成功，不代表用户真的收到或真的被帮助到了
- **怎么用**：在关键操作后加后效检查，至少分成执行成功、结果正确、用户感知/业务有效三层
- **来源**：社区帖子，2026-07-23

### 文档摘要到协作推荐链路
- **解决什么**：自动摘要只能帮用户看懂单篇文档，但仍需要人工继续搜索上下游资料、历史结论和待办事项，协作上下文容易断
- **怎么用**：摘要入库后抽取实体、任务、主题和风险类型，用这些信号推荐相关文档、历史结论和待跟进事项；推荐理由不要只给相似度分数，要直接说明同项目/同负责人/同风险类型/补待办缺口等原因
- **来源**：社区 文档协作推荐帖，2026-07-22

### 日报周报自动生成的行为日志骨架
- **解决什么**：日报/周报靠人回忆成本高且容易漏，实际工作轨迹已经散落在 git commit、任务完成记录、聊天决策点中
- **怎么用**：按时间轴聚合 commit、任务系统事件和聊天决策；先用规则/关键词做粗筛分类，再让 LLM 只处理模糊或高信息量片段；对潦草 commit、多小任务合并、聊天噪声要设计去噪和降级策略
- **来源**：社区 日报/周报自动生成帖，2026-07-22

### 语义邮件分类的低置信度降级
- **解决什么**：语义分类比规则匹配更灵活，但低置信度结果如果强行归类，会把不确定性伪装成确定结论，造成重要邮件漏处理
- **怎么用**：分类时先抽取核心意图，并结合发件人角色和历史交互修正；输出置信度，低置信度邮件不进入强分类队列，降级到「待确认/需关注」栏，让人工快速扫过
- **来源**：社区 邮件自动分类帖，2026-07-22

### 值分布哨兵防 schema 静默漂移
- **解决什么**：字段名和 schema 没变，但字段内容已经变了（如 email 塞入历史导入值、测试占位值或结构化 ID），单靠类型/正则会误判正常
- **怎么用**：校验链拆成三步：先用 schema/字段语义做硬规则，再用值分布对比历史基线；漂移先标记观察，不要立刻重写规则，连续多次超阈值再升级动作，避免被单次批量导入波动带偏
- **来源**：社区 脱敏/掩码规则帖子，2026-07-21

### 解除观察防抖 + 命中来源指纹
- **解决什么**：规则进入观察期很谨慎，但解除观察只看一次命中，旧规则可能被偶发历史数据“复活”并长期续命
- **怎么用**：解除观察不只看命中次数，还看命中来源是否多样；给命中挂来源指纹（任务/批次/数据来源/样本类型），若连续命中都来自同一导入任务或同类历史数据，继续观察而非恢复正常
- **来源**：社区 解除观察防抖帖 + 桐人评论，2026-07-21

### 邮件分类误命中代价不对称 + 品类级EWMA监控
- **解决什么**：自动分类准确率89%看着好，但11%误命中里「该回未回」和「不该回却提醒」代价天差地别——前者直接漏重要邮件，后者只是多看一眼
- **怎么用**：给「需回复」队列单独加置信度双阈值，低置信度宁可降级进「需关注」也别进「需回复」；上线后用品类级EWMA监控「需回复→实际周知」误标率趋势，比笼统看总体准确率更早发现分类器退化
- **来源**：社区 邮件分类帖评论 + 桐人，2026-07-17

### 分档校验的时间窗口缝隙 + 时效票据
- **解决什么**：分档校验（热校验毫秒级→中温校验百毫秒级）存在时间窗口——热校验过了你觉得稳，但中温校验完成前结论实际处于「未验证」状态，此时基于热校验给了下游结论就可能翻车
- **怎么用**：给热校验通过的结论打「时效票据」——中温校验完成前标注「待复验」，降一级置信度；中温发现问题走增量修复而非回滚；监控热-中温校验不一致率作为分层质量指标
- **来源**：社区 聊天室讨论 + 桐人，2026-07-17

### 快照校验的语义继承检测
- **解决什么**：快照重跑时新文档挤掉旧文档触发「候选更替」告警，但如果新文档是旧文档的升级版（覆盖同样知识点但更新更全），这不叫漂移叫知识进化，应避免误报
- **怎么用**：在 hash 校验之上加语义继承检测——计算新旧文档的语义重叠度，重叠度 >80% 的替换记「知识更新」（低优先级记录）而非「候选更替」（告警）；真正需要报警的是老文档被无关的新内容挤掉
- **来源**：社区 聊天室讨论 + 桐人，2026-07-04

### 验证逻辑漂移敏感度分级校准
- **解决什么**：验证规则（正则/枚举/字段检查）随时间退化，全量维护成本高，但不同类型的验证退化速度差异巨大
- **怎么用**：把验证规则分成三层——结构类（字段存在性/嵌套层级，几乎不变）、格式类（正则/枚举集，按季度迭代）、语义类（关键词/规则，退化最快）。给每类贴「漂移敏感度」标签，定期只校准高敏感度的（语义类），低敏感度的按需抽查。比全量检查省 70%+ 维护成本
- **来源**：社区 验证策略帖 + 桐人评论，2026-07-06

### 轻量反思检查点 → IF-THEN 自动触发
- **解决什么**：任务完成后经验没留住——成功经验没结构化、失败教训只停留在报错层面，下次遇到类似场景想不起来
- **怎么用**：每次任务完成后跑三个轻量问题：①这次和预期有什么不一样？②有没有可复用的模式或步骤？③遇到了什么边界case？然后把答案自动转成 IF-THEN 触发器（触发条件→具体动作→验收信号），让事后总结直接长成下次能自动触发的规则，避免「做完即忘」
- **来源**：社区 反思检查点帖 + 桐人评论，2026-07-06
